# 2. Executive conclusion

AX Terminal currently has a solid prototype-to-early-production foundation:

```text
Rust binary
    ↓
standalone Windows executable
    ↓
configuration file
    ↓
API client
    ↓
interactive authentication
    ↓
command registry
    ↓
tenant/system/audit operations
```

However, the project is not yet ready to be treated as a production-grade administrative control plane.

The most important issue is not that the binary is small or that the code is poorly structured.

The central issue is that the project currently has **insufficient release governance and operational safety around a high-privilege client**.

Current state:

```text
source code
    ↓
cargo build --release
    ↓
binary
    ↓
manual distribution
```

Target state:

```text
source
    ↓
tests
    ↓
static analysis
    ↓
security checks
    ↓
reproducible build
    ↓
artifact verification
    ↓
versioned release
    ↓
controlled distribution
    ↓
runtime configuration
    ↓
AX-Connect management API
```

# 3. P0 / Critical findings

## P0-1 — Production distribution documentation still instructs users to use a plaintext HTTP API

The README currently documents:

```text
AX_API_URL=http://localhost:4000
```

and describes the HTTP client as:

```text
no TLS (internal network)
```

This is incompatible with the intended AX-Connect production architecture.

AX Terminal should not be designed around direct access to:

```text
192.168.1.38:4000
```

or any other local LAN address for normal administrative operation.

The target should be a controlled HTTPS management endpoint.

Recommended:

```text
AX Terminal
    ↓ HTTPS
AX Management API
    ↓
AX-Connect platform
    ↓
Ubuntu infrastructure
```

The CLI should not directly expose the internal server as the public control plane.

---

## P0-2 — No CI/CD validation pipeline was found

No GitHub Actions workflow was found in the repository.

There is therefore no repository-enforced automatic pipeline guaranteeing:

- formatting
- compilation
- tests
- Clippy checks
- dependency checks
- release build verification

A high-privilege administrative CLI should not rely solely on a developer manually running:

```text
cargo build --release
```

before producing a binary.

Required minimum pipeline:

```text
push / pull request
        ↓
cargo fmt --check
        ↓
cargo check
        ↓
cargo test
        ↓
cargo clippy -- -D warnings
        ↓
release build
```

Security/dependency auditing should be added as a separate controlled step.

---

## P0-3 — Release artifact provenance is not yet established

The project claims a standalone Windows PE32+ executable.

However, there is no visible release process establishing:

- which commit produced a binary
- which Rust toolchain produced it
- which dependency lockfile was used
- whether the binary was generated by CI or manually
- whether the binary can be verified by checksum
- whether releases are signed

For a platform administration tool, this matters.

The future release should establish:

```text
version
commit SHA
build timestamp
toolchain
target triple
artifact SHA-256
```

and ideally a signed release artifact.

A compromised or accidental old binary should not be indistinguishable from the current production binary.

# 4. P1 / High-priority findings

## P1-1 — The README is already drifting from the actual intended architecture

The README states:

```text
dist/.env
```

must contain configuration.

It also states:

```text
AX_API_TOKEN
```

is for CI and automation.

This is operationally dangerous if a user copies a production `.env` containing a long-lived JWT into a distributable directory.

The recommended architecture is:

```text
binary
    ↓
secure runtime configuration
    ↓
interactive authentication
```

For automation:

```text
CI secret store
    ↓
short-lived credential
    ↓
non-interactive execution
```

Do not treat a local `.env` file beside a privileged binary as a secure secret-management system.

---

## P1-2 — The current release profile is optimized, but not enough for a production release process

The release profile contains:

```text
opt-level = 3
lto = true
codegen-units = 1
panic = "abort"
strip = true
```

This is a reasonable optimization configuration.

However, optimization is not release governance.

The project still needs:

```text
build validation
artifact naming
versioning
checksums
release notes
provenance
```

before the binary should be distributed as a trusted administration tool.

---

- authorization gates
- destructive confirmation

- audit logging

The project needs tests before major refactoring.

Minimum test groups:

```text

role mapping tests
authorization tests

tenant validation tests

audit tests
API response tests
```

---

## P1-4 — The dependency strategy is not yet production-hardened

`Cargo.lock` is committed, which is good.

However, the project currently has no visible automated dependency governance.

Recommended:

```text

    ↓
cargo audit
    ↓
dependency update policy
    ↓

```

Do not blindly update every dependency automatically in a high-privilege CLI.

Dependency updates should be reviewed because the binary is an administrative control plane.

# 5. P1 — Architecture and deployment findings

## P1-5 — Windows-only distribution is currently a hard platform constraint

The README says:

```text
Windows 10 / 11 x86-64
```

This is acceptable for the current operator workflow.

However, the AX ecosystem now includes an Ubuntu server.

The architecture should distinguish:

```text
AX Terminal
    = operator/admin client
```

from:

```text
Ubuntu server
    = AX-Connect infrastructure host
```

The Ubuntu server should not need to run the Windows CLI.

The future model is:

```text
Windows operator machine
        ↓
AX Terminal
        ↓ HTTPS
AX-Connect management API
        ↓
Ubuntu server infrastructure
```

If a Linux-native administration tool is eventually needed, that should be a deliberate target:

```text
x86_64-pc-windows-msvc
x86_64-unknown-linux-gnu
```

rather than accidentally coupling the CLI to the server.

---

## P1-6 — The `.env` configuration model should be replaced or hardened before production

The current design relies on:

```text
.env
```

beside the executable.

This is convenient for development but weak for production administration.

Problems:

- secrets may be copied with the binary
- file permissions may be wrong
- accidental backups may expose secrets
- configuration can be changed without an explicit deployment process
- a malicious local user may alter the API endpoint

A production design should separate:

```text
application binary
```

from:

```text
runtime configuration
```

and use a secure configuration mechanism appropriate to the operating system.

At minimum:

- validate the URL
- require HTTPS for non-localhost production endpoints
- reject suspicious schemes
- clearly distinguish development from production
- avoid long-lived tokens in `.env`

# 6. P2 / Important findings

## P2-1 — README claims "no runtime dependency" but does not define a release contract

The standalone binary claim is useful.

But production distribution needs a clear contract:

```text
AX Terminal v1.0.0
Target: Windows x86-64
Commit: abc123
SHA-256: ...
API compatibility: AX-Connect API v...
```

The CLI and API must have an explicit compatibility strategy.

Otherwise:

```text
new CLI
    ↓
old API
```

or:

```text
old CLI
    ↓
new API
```

may produce undefined operational behavior.

---

## P2-2 — No API compatibility/versioning strategy is documented

The CLI currently directly calls API paths.

As AX-Connect evolves, the CLI needs a compatibility contract.

Recommended:

```text
/api/v1/...
```

or a version negotiation mechanism.

The CLI should know:

```text
minimum supported API version
```

and fail clearly when incompatible.

---

## P2-3 — No documented failure/recovery model exists

The README documents successful commands, but not operational failure behavior.

A production operator needs to know what happens when:

```text
API unavailable
network timeout
authentication expires
server returns 401
server returns 403
server returns 429
server returns 500
audit delivery fails
```

This should be standardized.

---

## P2-4 — No release channel strategy exists

The project should eventually distinguish:

```text
development
staging
production
```

and possibly:

```text
stable
beta
nightly
```

A production operator should not accidentally use a development binary pointed at a production API.

# PART 1 — Configuration, Session, and API Transport

1. Production TLS path is not established.
2. Remote audit events can be silently lost.
3. HTTP transport is recreated per request.
4. Configuration validation is weak.
5. JWT-derived local role must never be authoritative.
6. Local config writes are not atomic.
7. Secret memory is not explicitly zeroized.
8. `.env` beside the binary is not a sufficient production secret-management system.
9. The API client needs centralized transport policy.
10. The production API boundary must be HTTPS management API, not direct LAN/server access.

---

# PART 2 — Command Execution and Security

11. Local authorization is UX-level only; server authorization is authoritative.
12. Destructive confirmation should be target-bound.
13. Remote audit must become durable and retryable.
14. Parser should return structured errors instead of silently ignoring malformed syntax.
15. Command argument validation should be schema-driven.
16. Two-role authorization is too coarse for future platform operations.
17. Persistent tenant selection needs explicit target precedence rules.
18. Local audit has no tamper-evident integrity protection.
19. Audit events should contain sanitized normalized arguments.
20. Login events should be auditable without credentials.
21. Audit failures should be visible/recoverable without crashing commands.
22. Non-interactive destructive operations must fail closed.
23. Terminal table width must use Unicode display width.
24. Command metadata is duplicated and can drift.
25. Central dispatch will become a scalability bottleneck.
26. Dynamic JSON should eventually be replaced with typed models for high-risk operations.
